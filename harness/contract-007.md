# Contract 007 — Deploy smoke (Vercel, fixture mode)
Backlog item: "Vercel deploy, key in env vars, fixture mode togglable for safe public URL. Done = live URL runs the full demo-learner loop."

This contract deploys FIXTURE MODE ONLY: project env vars are `MINSHUKU_FAKE_LLM=1` and `MINSHUKU_STORE=cookie`. **No `GEMINI_API_KEY` is configured anywhere in this contract** — live mode is a later env flip, documented in the README but not performed. Deploy via `npx vercel` CLI (authenticated as jeeminhan, project name `minshuku`): PREVIEW deployment first; production promote (`npx vercel --prod`) only after the evaluator passes C8–C12 against the preview URL.

Scope — four verified landmines plus one found in code review, with designs:

1. **Read-only serverless filesystem (state).** `web/lib/engine/storyStore.ts` persists ALL state to `web/.data/story-state.json`, and `runEpisode()` WRITES on every GET (it records `pending`) — both impossible on Vercel. But in fixture mode with the fixed demo clock/seed, the entire `StoryState` is a deterministic function of the day number: state-at-start-of-day-N = replay days 1..N−1 through the existing `runEpisode` + `completeEpisode` path (fast local computation, no LLM). Design: a `StoryStore` abstraction with two implementations — the existing file store (local default, behavior unchanged) and a cookie store selected by `MINSHUKU_STORE=cookie`. The cookie holds only `{ day, seeded, pending }`: `day` = current story day; `seeded` = whether the day-4 lesson batch applies (replay must append `day4LessonBatch()` at the day-4 boundary exactly as `web/scripts/seed-demo.ts` does — extract the batch into a shared module so seed-demo and the cookie store share ONE definition); `pending` = set by GET (via Set-Cookie), required and cleared by POST complete, preserving the existing 409-on-double-complete semantics. `runEpisode`/the routes must take the store via injection instead of calling `readStoryState`/`writeStoryState` directly. Requires refactoring `web/lib/engine/runEpisode.ts`, `web/lib/engine/storyStore.ts`, both API routes, and `web/scripts/seed-demo.ts` (which must keep using the file store).
2. **Read-only serverless filesystem (logs).** `runEpisode.ts` passes `WEB_LOG_DIR = join(process.cwd(), "..", "logs", "web")` and the engine `appendFileSync`s a scene-run log there — this write crashes on Vercel. In cookie mode, route log writes to `os.tmpdir()` (the only writable path); file mode keeps `logs/web` unchanged. Engine stays untouched — `logDir` is already a `runScene` parameter.
3. **Monorepo layout / tracing.** The app lives in `web/` but imports `../src/lib`, reads `../data` through the committed `web/data → ../data` symlink at runtime (`content.ts`: `join(process.cwd(), "data")`), and reads the kuromoji dictionary from `node_modules/kuromoji/dict/*.dat.gz` at runtime (`conjugation.ts`). Vercel project settings: Root Directory = `web`, "Include source files outside of the Root Directory" enabled (answer `web` at `vercel link`/first deploy; verify with `npx vercel project inspect minshuku` or the deploy output). `next.config.ts` already sets `outputFileTracingRoot` to the repo root; add `outputFileTracingIncludes` for the episode + complete routes covering `data/vocab.json`, `data/grammar.json`, `data/templates/**`, and `node_modules/kuromoji/dict/**` — these are dynamic `fs` reads the tracer cannot see. `web/fixtures/*.json` need NO include: `fixtureClient.ts` uses static JSON imports, so fixtures are bundled (verified). The `web/data` symlink's behavior under CLI upload + tracing must be VERIFIED during build, not assumed — if the symlink does not survive into the lambda such that `cwd/data` resolves to the traced files, fall back to including the files under both `../data/**` and `data/**` keys or whatever makes the runtime path resolve; C6 (local manifest) and C11 (live behavior) are the proof. Add `export const maxDuration = 60` to both API routes if the day-4 replay (3 episode replays + kuromoji dict load on cold start) approaches the default limit. Deployment Protection must be OFF for previews (the evaluator and the public hit the URL unauthenticated) — C8 pins this.
4. **Seeding on the deployed instance.** `npm run seed-demo` writes the local file — useless on Vercel. Design: `GET /demo` route handler that, in cookie mode, sets the cookie to `{ day: 4, seeded: true, pending: false }` and 303-redirects to `/`. Revisiting `/demo` after completing day 4 IS the reset-to-day-4 (idempotent). Day-1 reset = clear cookies / fresh browser context (no endpoint needed). In file mode, `/demo` must not silently half-work: either perform the same seeding as `seed-demo` through the shared code path, or return a clear JSON error pointing at `npm run seed-demo` — generator's choice, documented in the README.
5. **Determinism on a CDN.** Byte-identity criteria are pinned to the JSON BODY under the standing exclusions, never to headers. `/api/episode` responses must carry `cache-control` containing `no-store` (force-dynamic should already produce this — C10 verifies it live) so no stale episode or stale Set-Cookie is ever served from cache.

Files expected to change: `web/lib/engine/storyStore.ts`, `web/lib/engine/runEpisode.ts`, `web/lib/engine/demoLearner.ts` or a new shared lesson-batch module, a new cookie-store module under `web/lib/engine/`, `web/app/api/episode/route.ts`, `web/app/api/episode/complete/route.ts`, new `web/app/demo/route.ts`, `web/scripts/seed-demo.ts`, `web/next.config.ts`, root `README.md`. Plus Vercel project config (root dir, env vars, deployment protection) — record the preview URL and any bypass details in `harness/generator-state.md`.

Out of scope: live Gemini mode on the deployment (later env flip; README documents it, nobody performs it here); `GEMINI_API_KEY` in any Vercel environment; custom domain; auth or multi-user state (the cookie is one anonymous learner by design); a day-5 fixture (the day-5 fail-loud error is intended behavior, pinned in contract 006 C3 and re-pinned live in C10); engine code (`src/lib` read-only); any visual/UI changes (contract 006 owns the pixels).

## Evaluator review

### Code spot-checks

**1. Is state a pure function of `{ day, seeded }` in fixture mode?**

Confirmed. `demoReviewItems()` is a fixed seed with no external inputs. `demoClock(day)` is a pure function of day. `DEMO_PERSONA` is a constant. Fixture responses are keyed by day number and statically imported (bundled, not fs-read). `recentContext` and evolved `reviewItems` are fully derived by replaying days 1..N-1 through `runEpisode()` + `completeEpisode()`. The only branch is whether `day4LessonBatch()` items are appended, which is what `seeded` captures. The contract's determinism claim holds: given `{ day, seeded }`, the full `StoryState` is reproducible without any other mutable input. The implementation must ensure the cookie store's replay calls `runEpisode()` + `completeEpisode()` in the same sequence as `seed-demo.ts` does, never constructing SRS numbers by hand.

**2. Does `pending` preserve 409-on-double-complete? What does a second GET before POST do?**

In the current file store, `runEpisode()` calls `writeStoryState` setting `pending` to the full `PendingEpisode` object. A second GET before POST rewrites `pending` with the same value (fixture replay is deterministic) — no clobber, idempotent. In the proposed cookie store, `pending` is a boolean flag, and the full `PendingEpisode` data (result, templateId, itemOutcomes, passiveItems) is NOT stored in the cookie. This creates a subtlety: the POST complete route currently reads `state.pending` directly from the persisted state. With cookie store, POST must either re-run `runEpisode()` to reconstruct the pending data, or the cookie must encode enough for `completeEpisode()` to work. The contract says "pending = set by GET, required and cleared by POST" — treating it as a pure gate flag — but `completeEpisode()` needs the full pending object, not just the boolean. The generator must resolve this (likely: POST also calls `runEpisode()` in cookie mode to get the full pending data before calling `completeEpisode()`, then sets `pending: false` in the cookie). This is an implementation detail not blocking QA, but the generator must not skip it. The 409 semantics are sound: `pending: false` in cookie → reconstructed state has `pending: null` → `completeEpisode()` returns null → 409. Empty jar → `day` undefined → fresh state → `pending: null` → 409. Both cases correct.

**3. Is the `appendFileSync` landmine confirmed real?**

Confirmed. `src/lib/log/sceneRunLog.ts:14` calls `appendFileSync(path, ...)`. `runEpisode.ts` passes `WEB_LOG_DIR = join(process.cwd(), "..", "logs", "web")` to `runScene`. On Vercel, `process.cwd()` is `/var/task` (read-only); writing to `../logs/web` will throw. The fix (`os.tmpdir()` in cookie mode) is sound since `logDir` is already a `runScene` parameter.

**4. Are fixtures statically imported (no `outputFileTracingIncludes` needed)?**

Confirmed. `fixtureClient.ts` lines 3-6 use ES static `import` for all four day fixtures. These are bundled by Next.js at build time and need no NFT tracing entry. The claim in the contract is correct.

### Criterion-level findings

**C2 — jar state implicit between steps (b) and (d):** The original text says "(d) an immediate second POST (no intervening GET) → 409" without specifying the jar state. With `curl -c jar -b jar`, the jar IS automatically updated by (b)'s Set-Cookie response before (d) runs — so (d) uses the `pending: false` cookie from (b). This is correct behavior but was not explicit. Amended in C2 above: added "(jar now holds the day-2/pending-false cookie from step b)" and "(e)" now explicitly says "separate fresh empty jar (new curl invocation)".

**C3/C4 — dual-server start commands not specified:** The conventions block said only "file mode = port 3020, cookie mode = port 3021" without stating how to start them. The evaluator cannot infer whether to use `next start -p` or the standalone server. Added a sentence to the Conventions block specifying standalone server commands and noting the generator must confirm the exact form.

**C11 — Vercel CLI auth requirement unspecified:** `npx vercel env ls` requires the evaluator to be authenticated to jeeminhan's Vercel account. If the evaluator runs in a CI context without auth, this command silently fails or prompts interactively. Amended to `npx vercel env ls --token $VERCEL_TOKEN` and require the generator to document the auth mechanism in `harness/generator-state.md`.

**C10 — `x-vercel-cache` assertion:** "if present its value is never `HIT`" — the `never HIT` assertion could be vacuously true if Vercel doesn't emit this header at all on the preview URL. This is acceptable; it correctly pins the observable behavior rather than asserting the header's presence.

**C9 — "NOT Day 4:" assertion:** Correct and well-specified. After the second `/demo` visit in the same Playwright context, the cookie is reset to `{ day: 4, seeded: true, pending: false }`, so the story-so-far shows Days 1-3 summary lines only (Day 4's line only appears after completing Day 4). The NOT assertion properly verifies the reset.

**Missing criterion — C11 Vercel auth fallback:** If `$VERCEL_TOKEN` is not available to the evaluator, C11's `env ls` sub-check should fall back to accepting the generator's screenshot of the Vercel dashboard showing env vars, included in `harness/generator-state.md`. Not blocking but worth noting in C11.

### Verdict

ACCEPTED with the three clarifications above incorporated into the contract text (dual-server start commands in Conventions, C2 jar state explicit, C11 Vercel auth). No criterion requires revision — all are mechanically checkable. The unresolved implementation detail about how POST reconstructs `PendingEpisode` data in cookie mode is a generator concern, not a QA verifiability concern: C2 and C3 test the observable outputs (correct day, correct summary, correct debrief), not the internal reconstruction path.
